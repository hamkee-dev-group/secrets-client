# Browser encryption protocol

This document specifies the only supported wire format, `srs-browser-1`. The Rust
service cannot encrypt or decrypt it. Older server-encrypted records and APIs are
unsupported. The current browser-format database migrates from schema 2 to 3
to add management receipts without changing ciphertext or key derivation.

## Secrets and authority

The browser starts with an empty passphrase field. Senders can enter any nonempty
passphrase without a length cap; 12 or more characters is a recommendation only.
Inputs are not trimmed or Unicode-normalized. The optional Generate button uses
32 random bytes encoded as 43 unpadded base64url characters from the browser CSPRNG.
The server cannot inspect passphrases.

By default the passphrase is shared separately from the recipient link. The explicit
No passphrase option instead generates 32 random bytes, base64url encodes them and
uses that string as the input to the same derivation below. It is included only in
the recipient URL fragment: `/decrypt#id=<uuid>&key=<random-secret>`. It is not a
raw AES key. Anyone with the complete link can decrypt. Without this option, the
recipient link contains only `#id=<uuid>`.

Neither the passphrase, random link secret nor AES key is sent to the service.
The sender generates an independent random 32-byte management token; the wire
field remains `deletion_hash`. The private management link is
`/manage#id=<uuid>&token=<management-token>`. It authorizes receipt access and
revocation, never retrieval. Fragments are not included in HTTP requests but can
remain in browser or clipboard history. Loading either page is non-destructive;
retrieval and revocation require an explicit user action.

## Metadata and encoding

Metadata has exactly these fields; unknown fields are rejected:

| Field | Encoding / constraint |
| --- | --- |
| `version` | Integer `1` |
| `id` | Canonical lowercase UUIDv4 with RFC 4122 variant, generated by the client |
| `expires_at` | Integer Unix time in milliseconds, later than server time and at most 30 days ahead |
| `max_views` | Integer 0–100; 0 means unlimited until expiry; default is 1 |
| `salt` | 16 random bytes, unpadded base64url |
| `nonce` | 12 random bytes, unpadded base64url |

All binary strings use canonical RFC 4648 base64url without padding. The server and
client reject malformed or noncanonical encodings. Browser creation obtains time
from `/_health` before computing expiry, avoiding dependence on the user's clock.

Authenticated additional data is UTF-8 encoding of six fields joined with a single
LF, with no trailing LF:

```
srs-browser-1
<id>
<expires_at as decimal integer>
<max_views as decimal integer>
<salt as base64url>
<nonce as base64url>
```

Ciphertext is AES-256-GCM output with the 16-byte authentication tag appended.
The plaintext is 1–65,536 UTF-8 bytes, so ciphertext is 17–65,552 bytes. The tag is
always 128 bits; the nonce is always 96 bits. Every creation generates a new UUID,
salt and nonce, even when the sender reuses a passphrase. Encryption is never repeated
with the same derived key and nonce. There is no cipher negotiation or fallback.

## Key derivation

All client operations use native Web Crypto, without third-party JS or WASM:

1. `master = PBKDF2-HMAC-SHA256(UTF8(passphrase), salt, 600000, 32 bytes)`.
2. Import `master` as HKDF input key material.
3. Derive 32-byte outputs with HKDF-SHA256, using the same per-record salt and the
   exact UTF-8 `info` values below:
   - Encryption: `srs-browser-1/<id>/encryption`
   - Retrieval: `srs-browser-1/<id>/retrieval`
4. Import the encryption output as a non-extractable AES-GCM CryptoKey.
5. Encode the retrieval output as the retrieval token.

The fixed PBKDF2 cost simplifies validation and prevents attacker-selected work
factors. PBKDF2 is not memory-hard; generated random passphrases are strongly preferred.
The fixed cost is also applied to generated passphrases to keep one protocol path.
Server-stored hashes can support offline guessing of weak passphrases after database
theft. Hashing tokens does not remove that risk.

Store `SHA256(raw retrieval token)` and `SHA256(raw deletion token)`, each 32 bytes.
These are independent credentials; the deletion token is not derivable from the
recipient's passphrase. The server compares presented-token hashes in constant time.
Possession of a retrieval token permits view consumption, but does not directly
provide the AES key. Neither credential should be logged.

## API and transactions

| Request | Body | Result |
| --- | --- | --- |
| `GET /_health` | None | Health, source revision, version, current `now` in milliseconds |
| `POST /api/secrets` | `envelope`, `retrieval_hash`, `deletion_hash` | `201` with metadata |
| `GET /api/secrets/<id>/metadata` | None | Metadata only; no view consumed |
| `GET /api/secrets/<id>/status` | None | `metadata` and `remaining_views`; no view consumed |
| `POST /api/secrets/<id>/retrieve` | `{"token":"..."}` | Envelope; one view consumed |
| `POST /api/secrets/<id>/revoke` | `{"token":"..."}` | `204`; content deleted, receipt marked revoked |
| `POST /api/secrets/<id>/management` | `{"token":"..."}` | Private receipt; management token required |

An envelope is exactly `{"metadata":{...},"ciphertext":"..."}`. The entire creation
request is limited to 128 KiB. Client-supplied ciphertext is opaque; the server can
validate size and encoding but cannot prove that a malicious client encrypted it.

Retrieval acquires a SQLite immediate transaction, reads an unexpired record,
checks the retrieval credential, leaves unlimited records unchanged or decrements
remaining views or deletes the final limited record, commits, and only then returns ciphertext. Revocation independently verifies
the deletion credential within its transaction. Failed credentials consume nothing.
Concurrent requests across database connections cannot exceed the allowance.

The browser checks availability on page load without consuming a view. On Reveal it derives credentials,
submits the retrieval token, checks that returned metadata matches, and authenticates
and decrypts the ciphertext locally. Wrong passphrases produce invalid retrieval tokens.
Metadata tampering can cause rejection or a later decryption failure; ciphertext
corruption can be discovered only after retrieval. A successful authorization is not
proof of delivery, successful decryption, reading, identity or destruction of copies.

Requests are never automatically retried. A timeout, disconnect or browser crash
can happen after commit and lose a view. Cancellation does not release a database
worker permit while its blocking operation is still running.

Errors contain only `{"error":"non-sensitive message"}`: 400 malformed input,
401 invalid credential, 404 unavailable record, 409 duplicate ID, 413 oversized body,
429 rate limit, 503 worker saturation, 507 quota, 408 timeout, 500 storage failure.
The API returns no decryption keys, passphrases, plaintext or stored credential hashes.

## Expiration

SQLite indexes `expires_at`. At startup, and after each wake-up, the scheduler deletes
due records and queries the earliest remaining expiry. It registers a Tokio notification
before that query, so a concurrent insertion cannot lose its wake-up. It waits for
that deadline or a record-change notification; an empty store waits indefinitely.
Errors use a one-second retry delay and a non-sensitive diagnostic.

All writes in a running deployment must go through its single API process so the
scheduler receives notifications. Direct administrative writes and multiple independent
API processes are unsupported. Retrieval always checks the current database expiry,
independent of cleanup. System-clock changes or scheduling delays can delay physical
cleanup; they do not grant access to a record already expired according to server time.


The status endpoint reports a snapshot of remaining views. It can change immediately
after the response. `remaining_views` is mutable server state, not authenticated
metadata; it is never included in key derivation or AES-GCM additional data.

## Management receipts

One receipt row per secret records `status` (active, consumed, revoked or expired),
`max_views`, `views_used`, `last_accessed_at`, `failed_attempts`, `last_failed_at`,
`ended_at`, `expires_at` and `receipt_expires_at`. Times are Unix milliseconds;
unknown event times are null. The receipt has no plaintext, ciphertext, salt, nonce
or retrieval verifier. Its stored management-token hash is never returned.

Successful retrieval increments views and records the last access in the same
transaction as ciphertext delivery authorization. A final limited retrieval marks
consumed and removes ciphertext. Revocation removes ciphertext immediately.
Expiration marks only active receipts expired, preserving earlier terminal states.
Receipts are removed at original expiry plus 86,400,000 milliseconds. The scheduler
uses both content and receipt deadlines. Both are checked on access as well.

Failed attempts count well-formed retrieval credentials rejected against a live
secret. Malformed requests, rate-limited requests, unavailable secrets and failed
management requests are not counted. Counts and timestamps do not identify people,
prove successful decryption or establish that a recipient read anything.

Receipt reads use POST to keep credentials out of URL paths/query strings and
return 404 for both missing receipts and incorrect management credentials.
Retained receipt IDs cannot be reused. Receipt rows count toward the record quota;
ciphertext has its separate byte quota. Existing limited secrets migrate their
used-view count; pre-migration timestamps and failures are unavailable, and past
unlimited-view accesses cannot be reconstructed.
